## Governance: the hard gate

A dataset is used only through its `manifest.json`. The manifest has a strict schema and holds no personal data: owners and annotators are role codes, and the free-text fields only accept short neutral codes.

The manifest records:
- dataset id, version, type, kind, case count, SHA-256 and collection date;
- owner (a role) and collection source;
- consent status and what it covers: image processing, appearance analysis, evaluation, provider transmission;
- permitted uses, retention date, deletion process and who is responsible for it;
- access, encryption at rest, and whether raw storage and derived labels are allowed;
- whether the data may leave the evaluation environment;
- **provider transmission per provider**;
- legal review status (PENDING, APPROVED or REJECTED);
- annotation status and version, the holdout ids, and sensitivity.

| Gate | Refuses when |
|---|---|
| `governanceGate(use)` | the use is not permitted; the retention date has passed; real data has consent that is not documented, or does not cover processing and evaluation (selfies also need appearance analysis and sensitivity `high`); legal review is REJECTED |
| `providerTransmissionGate(provider)` | everything above, plus: transmission not allowed for this dataset or for this provider; the data may not leave the environment; real data whose consent does not cover provider transmission; legal review not APPROVED (PENDING is never treated as approval) |

A refusal is reported as `BLOCKED — DATA GOVERNANCE` with its reasons, and nothing is read or sent. "Test data" is never assumed to be safe to upload.

## Dataset structure (outside Git)

```
<root>/                               created by: validate.ts --init --root=<dir>
  registry.json                       append-only: (dataset, version) → sha256 (immutable versions)
  TEMPLATE.manifest.json              consent "pending", transmission off
  vision/<datasetId>/<version>/       manifest.json · cases.json · annotations.json · files/<image>
  color-profile/<datasetId>/<version>/  same (sensitivity "high")
  stylist/ratings.json + stylist/blinding-key.json   blind human ratings (optional)
```

- The content SHA-256 covers `cases.json`, `annotations.json` and every image, in order. It must equal the manifest's `sha256` before any use; otherwise the run stops with `DATASET_INTEGRITY_FAILURE`.
- Each image is re-hashed right before it is read.
- Changing one case or label means a new version. The registry refuses the same version with different content.
- The repository holds code only. A test asserts that no image or dataset file is tracked. Results are written outside the repository; the scripts refuse a path inside it.

## Ground truth and annotation

`annotations.json` holds independent human labels: provider output is never ground truth.
- Each field has a catalog value or `unknown` (nobody is forced to guess), plus a confidence of high, medium or low.
- Annotators are opaque codes (A1, A2…), and the file must attest `blindToProvider: true`.

| Annotators' labels | Final ground truth |
|---|---|
| all agree | agreed |
| disagree, with an adjudication recorded | adjudicated (the original labels are kept) |
| disagree, no adjudication | unresolved: **not scored** |
| everyone `unknown` | unknown: **not scored** |
| one annotator | single, reported as `LIMITATION — SINGLE ANNOTATOR` |

The report includes per-field agreement: compared, agreed, disagreed, unresolved and the agreement rate.

**Vision fields:**
- category, subcategory, primary colour, secondary colour (`none` allowed);
- pattern, material, sleeve length, fit, style, season (compared as a set), gender, formality;
- subject: single garment, multiple garments, no garment or unclear.

**Colour-profile fields:** these separate what is observable from expert judgement.
- Observable: photo quality acceptable, contrast.
- Expert judgement: undertone (warm, neutral or cool) and season.
- A season is a styling convention, not a biological fact. It is compared only where at least two experts agree, or an adjudication exists.
- No demographic, ethnic or identity label is collected or inferred.

## Holdout policy

- `manifest.holdout` lists the holdout cases. The rest are split deterministically, by a hash of the id, into development and validation.
- `prompt_development` sees only development cases, and `evaluation` sees only validation cases. Only an explicit `--purpose=final_evaluation` sees the holdout, and nothing else.
- Holdout failures are never used to tune prompts in the same cycle.
- The same examples are never used for prompt tuning, evaluation, calibration and (future) fine-tuning.

## Validation workflow

```bash
cd apps/web
bun scripts/ai-eval/real-data/validate.ts --init --root=/secure/real-validation      # once: structure + template
# collect, consent, annotate (blind), write manifest.json + cases.json + annotations.json, compute sha256
bun scripts/ai-eval/real-data/validate.ts --root=/secure/real-validation --out=/secure/results/$(date -u +%Y%m%dT%H%M%SZ) \
  [--purpose=evaluation|final_evaluation|prompt_development] [--max-calls=N] [--max-cost-usd=X] [--transmit-constructed]
```

| Capability | What runs |
|---|---|
| Vision | the app's pipeline (`prepareVisionImage` → schema → `interpretGarmentOutput` → colour cross-check), with the app's single retry and the Phase 5.1 ledger, budget and circuit breaker. Every provider gets the same images, preprocessing (`vision-prep-v1`), prompt and schema version, in the same order. There is no provider-specific tuning. |
| Colour profile | the deterministic analyser `color-analysis-v2`, unchanged, run locally. No provider; the image bytes are dropped after analysis. |
| Stylist | the 60-case **constructed** corpus `constructed-v1`. All cases are Uzbek: 59 in Latin script and 1 with Cyrillic input. It covers casual, work, formal, date, travel, sport, weather, seasonal, limited wardrobe, missing information, follow-ups, colour profile, mixed language and safety. Provider calls need `--transmit-constructed`, credentials, explicit models and `--max-calls`. Human rubric scores (1–5: relevance, usefulness, completeness, Uzbek quality, grounding, safety) come from blind raters: the answers are labelled X1…, and the key mapping labels to providers is a separate file. |
| Outfit | 20 **constructed** contexts against the deterministic engine, unchanged. The checks are written independently of the engine's scoring: validity, the expected problem for incomplete wardrobes, cold/heat/rain rules, formal occasion rules, layering, disliked colours and determinism (same input, and the wardrobe in a different order). Colour harmony is NOT_EVALUATED. Failed checks are findings; this phase does not change the engine. |

**Provider execution** needs all of:
1. the governance gate;
2. explicit provider transmission;
3. credentials;
4. an explicit model;
5. a call cap;
6. content-free accounting.

Otherwise the section is BLOCKED or NOT_TESTED. A mock is never substituted.

## Metrics

Every metric is shown as **correct / scored**, never as a bare percentage.
- A field without ground truth is not scored and is counted in `unscoredFields`.
- Provider errors and invalid outputs are counted separately, and are never averaged into accuracy.
- An empty denominator gives `null` (N/A), never 0.

| Capability | Metrics |
|---|---|
| Vision | schema validity; subject accuracy; per-field accuracy; false acceptance (non-garment, multiple or unclear accepted as a garment); false rejection; multiple / unclear / no-garment handling; latency, tokens and cost from Phase 5.1 accounting; **PRELIMINARY CONFIDENCE ANALYSIS**: correctness per raw-confidence bin, which is not calibration (Phase 5.3) |
| Colour profile | quality rejection (a confusion table against the experts); contrast and undertone agreement; season agreement (expert consensus only); abstentions; PRELIMINARY confidence (mean confidence when correct vs wrong) |
| Stylist | automatic: grounding, hallucination, references, injection resistance. Human, per dimension with n and the score distribution: relevance, usefulness, completeness, Uzbek quality, grounding, safety, plus inter-rater agreement. |
| Outfit | cases passing every check; failures by check; determinism |

**Statistical caution:** sizes are small (target: 50–100 garments, 20–50 selfies, 60 stylist cases). Results are preliminary. Show raw counts. Do not claim that one provider is better from small samples.

## Reproducibility

Every report records:
- the run id and timestamp;
- the app commit, and whether the working tree was clean;
- the purpose;
- the vision, stylist and outfit prompt versions, the outfit engine version, the colour analysis version and the preprocessing version;
- the evaluation version (`real-validation-v1`);
- each dataset's id, version, SHA-256 and case count;
- the provider and model per section, and the budget used.

Never recorded: secrets, personal data, images, file names, paths, prompts or responses.

## Privacy

- Reports hold case ids (neutral codes), labels, counts and error kinds only.
- Image quality metadata is limited to width, height, format, size and orientation, plus whether EXIF was present. EXIF content is never read.
- The app's preparation strips EXIF, XMP and IPTC (verified per image).
- Selfies:
  - never enter Git, logs, telemetry, snapshots or public storage;
  - are analysed locally;
  - are deleted on the retention date through the manifest's deletion process.
- No face embeddings or biometric identifiers are computed.

## Deletion procedure

1. On `retentionUntil` the gate refuses the dataset.
2. The responsible role deletes `files/` with secure deletion, then keeps or deletes the derived labels according to `derivedLabelsAllowed`.
3. Delete the result directories that hold per-case labels.
4. Keep the registry entry (id, version and hash only) as the audit trail.

## Correction log (future evidence)

- `WardrobeItem.correctionLog` records `{field, from, to, at}`, and the item keeps `analysisProvider`, `analysisModel`, `analysisVersion` and `analyzedAt`. Together these are enough to measure, later, which provider/model/version a user corrected.
- No schema change is needed.
- This is **evaluation evidence, never automatic training data**. Any use of production corrections needs its own consent and governance review.
