# B4 — Wardrobe and media, storage drivers, upload limits

Started at `2b1ed74` (2026-11-26). Stage goal and exit criteria: `docs/plan/README.md`.
Binding: ADR 0001, 0002, 0003, 0007, 0008, 0009 (image processing);
`.claude/skills/lookly-go-backend/references/porting.md` (media rules, defects not to
copy); `.claude/skills/lookly-security/references/checklists.md` (uploads and media,
quotas and abuse).

## Problem

The Go service cannot store or show a garment. The wardrobe (list, read, correct,
delete, upload) and the private images behind it still depend on the Next.js API, which
also has defects to leave behind: no per-user upload limit or wardrobe size, image files
left behind when a request fails half way, and images only on the server's own disk.

## Solution

The Go service serves `listWardrobeItems`, `createWardrobeItem`, `getWardrobeItem`,
`updateWardrobeItem`, `deleteWardrobeItem` and `getMedia` with the contract's responses
and error codes, on the shared database and the same storage layout. Images are
processed in Go (ADR 0009) and kept either on the local disk or in Cloudflare R2, chosen
by configuration. Every user can upload 100 images a Tashkent day and keep 1000 items.
Garment analysis in this stage is the development mock, ported exactly; real providers,
quotas and background analysis are stage B6.

## User stories

1. As a user, I want to upload a photo of a garment and get it back as an item with its
   detected attributes, in one request.
2. As a user on a bad connection, I want a retried upload (same `Idempotency-Key`) to
   give me the item once, never twice.
3. As a user, I want my wardrobe newest first, filtered by category, page by page.
4. As a user, I want to open one item, correct its attributes, and see what I corrected.
5. As a user, I want to delete an item and its images.
6. As a user, I want my images shown only to me: links that expire, and nothing served
   for a key that is not signed.
7. As a user, I want my photo's location and camera data never stored, and my photo
   shown upright.
8. As the operator, I want each user limited to 100 uploads a day and 1000 items, so
   that one account cannot run up storage costs (owner decision, 2026-11-26).
9. As the operator, I want images in R2 or on the local disk by one setting, and the
   server refusing to start with incomplete storage settings.
10. As the operator, I want image files nobody references removed, and no file left
    behind by a failed upload.

Unhappy paths, each with the contract's code:
- no file, a form that is not multipart: `BAD_REQUEST`, `UNSUPPORTED_MEDIA_TYPE`;
- a declared type that is not an image, a file over 8 MB, a body over 10 MB:
  `UNSUPPORTED_IMAGE_FORMAT`, `PAYLOAD_TOO_LARGE`;
- HEIC, HEIF, AVIF or another format by content: `UNSUPPORTED_IMAGE_FORMAT` (415);
- bytes that do not decode: `INVALID_IMAGE` (422); shortest side under 256 px, a side
  over 8000 px, more than 40 MP: `IMAGE_DIMENSIONS` (422);
- the same `Idempotency-Key` with another payload: `IDEMPOTENCY_KEY_MISMATCH`; while the
  first is running: `IDEMPOTENCY_IN_PROGRESS` with `Retry-After`; a malformed key:
  `VALIDATION_ERROR`;
- 100 uploads today: `RATE_LIMITED` with `Retry-After` (to the next Tashkent midnight);
  1000 items: `RATE_LIMITED` without a time to wait (see Decisions);
- an item that is not the user's, or does not exist: `NOT_FOUND`;
- a correction that does not fit (a subcategory of another category): `VALIDATION_ERROR`;
- a media link with a bad signature, an expired one, or a key we never generate: 404;
- consent out of date: `CONSENT_REQUIRED`; no session: `UNAUTHORIZED`.

## Decisions

Each is a default (decided here, not by the owner) unless marked.

**Contract and parity**
- Request rules (the PATCH body, the list query, the `Idempotency-Key` header) are judged
  as the Next.js schemas judge them: golden vectors from the real schemas, as in B2/B3.
- Responses keep the Next.js shape exactly (`serializeWardrobeItem`): lists decoded,
  times in milliseconds, images as signed URLs (`url` is the display variant, or the
  master for images uploaded before variants existed), `primaryImage`.
- The catalog (categories, subcategories by category, colours with their hex values,
  patterns, materials, sleeve lengths, fits, styles, seasons, genders, formalities) is
  read into Go from a JSON copy generated from the TypeScript catalog; a test in each
  app fails when they differ (as the legal texts in B3).
- Signed media URLs are the Next.js ones byte for byte (`HMAC-SHA256(secret, key + "\n"
  + exp)`, base64url; `MEDIA_SIGNING_SECRET`, `MEDIA_URL_TTL_SECONDS`, absolute with
  `PUBLIC_BASE_URL`): golden vectors, so a link one server signed works on the other.
  Go is stricter with the settings: a lifetime that is malformed or outside 60 s – 24 h
  stops the server (Next.js used the default for a malformed one and had no limits),
  and so do white space around the secret and the same secret as `JWT_SECRET`.
- `GET /api/v1/media/...` is served by hand: every path under the prefix is the route
  and the rest is the key (the generated pattern matches one segment; the router's
  wildcard redirects `..` and `//` paths). Every refusal is 404, as in Next.js, including
  a missing `exp` or `sig` (the contract's 400 is never used, as before).
- The gate runs before the generated router reads path and query parameters, so a
  caller without a session is answered 401 whatever its parameters (needed by the list
  query in B4.4).

**Images** (ADR 0009)
- Accepted by decoded content only: JPEG, PNG, WebP. The declared type must still be one
  of the image types the old API accepted (it refuses before reading the bytes).
- Header read first: format, dimensions (after orientation), at most 40 million pixels,
  before any pixel is decoded. Past 40 million pixels the answer is `IMAGE_DIMENSIONS`;
  the old API answered `INVALID_IMAGE` there (sharp's pixel limit failed the decode),
  which says the file is broken when it is only too large.
- Differences from sharp (ADR 0009), each tested: masters keep their pixel type only
  when they need no turning (a turned picture is written with 8 bits per channel);
  animated WebP and 12-bit JPEG are refused as unreadable; the variants' bytes differ
  (other resampling and encoder), their sizes, formats and orientation do not.
- Stored as now: `users/<owner>/<uuid>.<jpg|png|webp>` (master, never served),
  `_display.webp` (≤ 1600 px, quality 82), `_thumb.webp` (≤ 400 px, quality 75); size and
  SHA-256 of the uploaded bytes recorded.
- At most two images are processed at the same time per server (each can take hundreds
  of megabytes while decoded); the others wait, within the request's time limit. The
  header checks (format, dimensions, pixel count) run before the wait, so a refused
  file is answered at once, never behind other uploads.

**Storage**
- One interface with two drivers: `local` (a directory, as the Next.js server lays it
  out) and `r2` (Cloudflare R2 through its S3 API: endpoint, bucket, access key id and
  secret from the environment; the secret is never printed).
- Images are always served through `GET /api/v1/media/...` with the signed link, from
  either driver: no presigned R2 links (they would change the host the apps load from,
  and the link format the contract and the apps know).
- The local driver writes a file under a temporary name and renames it into place, so a
  reader never sees half a file. Keys are checked against the pattern of the keys we
  generate before any path or object name is built.
- A failed upload removes what it stored before answering. A deleted item's files are
  removed after its rows are gone; if that fails, the sweep removes them later.
- The sweep (the old manual script, now an hourly worker job): files no image row
  references and older than one hour are deleted, re-checked just before deletion;
  files whose names we never generate are reported, never deleted.

**Wardrobe**
- The list's cursor is an item id of the user's: the page continues after it (newest
  first, then by id). A cursor that is not one of the user's items gives an empty last
  page, as the old API did for an unknown id.
- A correction records each changed field (`from`, `to` as the old API wrote them, and
  the time), sets `wasCorrected`, and changes nothing when nothing differs. A change and
  its log entry are one statement.
- Analysis in this stage: the development mock, ported exactly (colours from a 32×32
  resample of the pixels, the file-name hints, the confidences). `AI_VISION_PROVIDER`
  other than `mock` is refused at start until B6, and the mock is refused in production
  unless `AI_ALLOW_MOCK_IN_PRODUCTION=1` (the Next.js rule).

**Limits** (owner decision, 2026-11-26: 100 a day, 1000 items)
- Uploads: 100 per user per Tashkent day, counted when the image is accepted and before
  it is processed; a failed upload gives its attempt back; a replay is not counted. The
  answer is `RATE_LIMITED` with `Retry-After` up to the next Tashkent midnight.
- Items: at most 1000 per user, checked under the user's lock in the transaction that
  creates the item. The answer is `RATE_LIMITED` with its own message (delete items
  first), without `Retry-After`: the contract has no better code, and a new one would
  change the clients.

## Contract impact

None planned. The item limit uses `RATE_LIMITED`, which the contract lists for this
operation; its `Retry-After` is absent there, which the contract allows.

## Testing

Seam: the HTTP handlers over the real router, gate and PostgreSQL; image processing on
generated images and fixtures; storage drivers on a temporary directory and on a real
S3-compatible server (MinIO) for `r2`.

- Body, query and header rules: every golden case.
- Catalog: equal to the TypeScript one.
- Signed URLs: golden vectors (sign and verify), expiry, tampering, key pattern.
- Images: each accepted format (with alpha, 16-bit PNG, progressive JPEG), every EXIF
  orientation 1–8 (result upright, width and height swapped for 5–8), HEIC/AVIF brands,
  garbage, truncated files, dimension and pixel limits at and past their boundaries,
  metadata gone from every variant, variant sizes; fuzzing of the decoders' entry.
- Mock vision: golden vectors from the TypeScript mock on solid and two-colour images,
  and the file-name hints.
- Upload: success, each refusal above with nothing stored (no row, no file), idempotent
  replay, mismatch, in progress, takeover after 5 minutes; the limits (100th and 101st
  upload, Tashkent midnight, 1000th and 1001st item, concurrent uploads at the limit).
- List, read, correct, delete: ownership (another user's item is `NOT_FOUND`), pages and
  cursors, the correction log, files removed.
- Media: served with its headers, 404 for every bad link, from both drivers.
- Sweep: orphans older than the minimum age removed, recent ones and referenced ones
  kept, unknown names reported.
- Config: every storage and vision rule, fail closed, secrets not printed.
- e2e: `wardrobe.spec.ts` passes in Go mode with the wardrobe and media operations
  answered by Go; the specs that upload (outfits, stylist, colour profile) keep passing.

## Out of scope

- Real vision providers, the AI quota, analysis as a background job (B6).
- HEIC support (the apps convert before upload).
- Range requests and CDN caching for media.
- Moving existing images between drivers (a deployment step with the owner's approval,
  rule 8).
- The display-variant backfill script (images from before variants are served from the
  master, as now).
