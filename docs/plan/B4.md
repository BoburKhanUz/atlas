# B4 — Wardrobe and media, storage drivers, upload limits

Started at `2b1ed74` (2026-11-26). Stage goal and exit criteria: `docs/plan/README.md`.
Binding: ADR 0001, 0002, 0003, 0007, 0008, 0009 (image processing);
`.claude/skills/lookly-go-backend/references/porting.md` (media rules, defects not to
copy); `.claude/skills/lookly-security/references/checklists.md` (uploads and media,
quotas and abuse).

## Problem

The Go service cannot store or show a garment. The wardrobe (list, read, correct,
delete, upload) and the private images behind it still depend on the Next.js API, which
also has defects to leave behind: no per-user upload limit or wardrobe size, image files
left behind when a request fails half way, and images only on the server's own disk.

## Solution

The Go service serves `listWardrobeItems`, `createWardrobeItem`, `getWardrobeItem`,
`updateWardrobeItem`, `deleteWardrobeItem` and `getMedia` with the contract's responses
and error codes, on the shared database and the same storage layout. Images are
processed in Go (ADR 0009) and kept either on the local disk or in Cloudflare R2, chosen
by configuration. Every user can upload 100 images a Tashkent day and keep 1000 items.
Garment analysis in this stage is the development mock, ported exactly; real providers,
quotas and background analysis are stage B6.

## User stories

1. As a user, I want to upload a photo of a garment and get it back as an item with its
   detected attributes, in one request.
2. As a user on a bad connection, I want a retried upload (same `Idempotency-Key`) to
   give me the item once, never twice.
3. As a user, I want my wardrobe newest first, filtered by category, page by page.
4. As a user, I want to open one item, correct its attributes, and see what I corrected.
5. As a user, I want to delete an item and its images.
6. As a user, I want my images shown only to me: links that expire, and nothing served
   for a key that is not signed.
7. As a user, I want my photo's location and camera data never stored, and my photo
   shown upright.
8. As the operator, I want each user limited to 100 uploads a day and 1000 items, so
   that one account cannot run up storage costs (owner decision, 2026-11-26).
9. As the operator, I want images in R2 or on the local disk by one setting, and the
   server refusing to start with incomplete storage settings.
10. As the operator, I want image files nobody references removed, and no file left
    behind by a failed upload.

Unhappy paths, each with the contract's code:
- no file, a form that is not multipart: `BAD_REQUEST`, `UNSUPPORTED_MEDIA_TYPE`;
- a declared type that is not an image, a file over 8 MB, a body over 10 MB:
  `UNSUPPORTED_IMAGE_FORMAT`, `PAYLOAD_TOO_LARGE`;
- HEIC, HEIF, AVIF or another format by content: `UNSUPPORTED_IMAGE_FORMAT` (415);
- bytes that do not decode: `INVALID_IMAGE` (422); shortest side under 256 px, a side
  over 8000 px, more than 40 MP: `IMAGE_DIMENSIONS` (422);
- the same `Idempotency-Key` with another payload: `IDEMPOTENCY_KEY_MISMATCH`; while the
  first is running: `IDEMPOTENCY_IN_PROGRESS` with `Retry-After`; a malformed key:
  `VALIDATION_ERROR`;
- 100 uploads today: `AI_QUOTA_EXCEEDED` with `Retry-After` (to the next Tashkent
  midnight); 1000 items: `VALIDATION_ERROR` with its own message (see Decisions);
- every processing slot busy for the whole of the request's time, or too many uploads
  at the same time (two of one user, sixteen in all): `AI_UNAVAILABLE` with
  `Retry-After`, nothing stored;
- the account deleted while its upload runs: `UNAUTHORIZED`, nothing stored;
- an item that is not the user's, or does not exist: `NOT_FOUND`;
- a correction that does not fit (a subcategory of another category): `VALIDATION_ERROR`;
- a media link with a bad signature, an expired one, or a key we never generate: 404;
- consent out of date: `CONSENT_REQUIRED`; no session: `UNAUTHORIZED`.

## Decisions

Each is a default (decided here, not by the owner) unless marked.

**Contract and parity**
- Request rules (the PATCH body, the list query, the `Idempotency-Key` header) are judged
  as the Next.js schemas judge them: golden vectors from the real schemas, as in B2/B3.
- Responses keep the Next.js shape exactly (`serializeWardrobeItem`): lists decoded,
  times in milliseconds, images as signed URLs (`url` is the display variant, or the
  master for images uploaded before variants existed), `primaryImage`.
- The catalog (categories, subcategories by category, colours with their hex values,
  patterns, materials, sleeve lengths, fits, styles, seasons, genders, formalities) is
  read into Go from a JSON copy generated from the TypeScript catalog; a test in each
  app fails when they differ (as the legal texts in B3).
- Signed media URLs are the Next.js ones byte for byte (`HMAC-SHA256(secret, key + "\n"
  + exp)`, base64url; `MEDIA_SIGNING_SECRET`, `MEDIA_URL_TTL_SECONDS`, absolute with
  `PUBLIC_BASE_URL`): golden vectors, so a link one server signed works on the other.
  Go is stricter with the settings: a lifetime that is malformed or outside 60 s – 24 h
  stops the server (Next.js used the default for a malformed one and had no limits),
  and so do white space around the secret and the same secret as `JWT_SECRET`.
- `GET /api/v1/media/...` is served by hand: every path under the prefix is the route
  and the rest is the key (the generated pattern matches one segment; the router's
  wildcard redirects `..` and `//` paths). Every refusal is 404, as in Next.js, including
  a missing `exp` or `sig` (the contract's 400 is never used, as before).
- The gate runs before the generated router reads path and query parameters, so a
  caller without a session is answered 401 whatever its parameters (needed by the list
  query in B4.4).

**Images** (ADR 0009)
- Accepted by decoded content only: JPEG, PNG, WebP. The declared type must still be one
  of the image types the old API accepted (it refuses before reading the bytes).
- Header read first: format, dimensions (after orientation), at most 40 million pixels,
  before any pixel is decoded. Past 40 million pixels the answer is `IMAGE_DIMENSIONS`;
  the old API answered `INVALID_IMAGE` there (sharp's pixel limit failed the decode),
  which says the file is broken when it is only too large.
- Differences from sharp (ADR 0009), each tested: masters keep their pixel type only
  when they need no turning (a turned picture is written with 8 bits per channel);
  animated WebP and 12-bit JPEG are refused as unreadable; the variants' bytes differ
  (other resampling and encoder), their sizes, formats and orientation do not. The
  thumbnail's size is computed from the picture's own size, as sharp computes it, not
  from the display variant's (the two round differently for some sizes).
- A file whose header and pixels disagree about its size is refused as unreadable: the
  limits were checked against the header.
- A decoder (the standard library's, `x/image`'s) that panics on a picture refuses the
  picture as unreadable, and the panic is logged with its stack (`DecoderPanic`); a
  panic in our own code is not caught there: it is a bug, answered as an internal error.
- Stored as now: `users/<owner>/<uuid>.<jpg|png|webp>` (master, never served),
  `_display.webp` (≤ 1600 px, quality 82), `_thumb.webp` (≤ 400 px, quality 75); size and
  SHA-256 of the uploaded bytes recorded.
- At most two images are processed at the same time per server (each can take hundreds
  of megabytes while decoded); the others wait, within the request's time limit. The
  header checks (format, dimensions, pixel count) run before the wait, so a refused
  file is answered at once, never behind other uploads.

**Storage**
- One interface with two drivers: `local` (a directory, as the Next.js server lays it
  out) and `r2` (Cloudflare R2 through its S3 API: endpoint, bucket, access key id and
  secret from the environment; the secret is never printed). The R2 driver is a small
  client of our own, with no new dependency (ADR 0010).
- The driver is never guessed: settings of the bucket without `STORAGE_DRIVER` stop the
  server. At start a bucket that refuses the request (its name, the credentials) stops
  `serve` and `worker`; one that does not answer is logged and they start.
- Until the cutover both servers share the storage, and the Next.js server has the
  local driver only: `r2` is for after the cutover, or for a deployment of the Go
  server alone. Moving existing images is a deployment step (out of scope).
- Images are always served through `GET /api/v1/media/...` with the signed link, from
  either driver: no presigned R2 links (they would change the host the apps load from,
  and the link format the contract and the apps know).
- The local driver writes a file under a temporary name, puts it on the disk (`fsync`
  of the file, then of its directory) and renames it into place, so neither a reader
  nor a power cut sees half a file. Keys are checked against the pattern of the keys we
  generate before any path or object name is built.
- A failed upload removes what it stored before answering. A deleted item's files are
  removed after its rows are gone; if that fails, the sweep removes them later.
- The sweep (the old manual script, now a worker job, `storage_sweep`, run hourly and
  when the worker starts): files no image row references and older than one hour are
  orphans. A run first goes through the whole storage, asking the database owner by
  owner, then removes the orphans, each asked about once more just before it is
  removed; files whose names we never generate are reported, never deleted. Two
  safeguards the script did not have, because this one runs unattended; in both
  nothing is removed and the job fails, so that somebody looks:
  - a database without a single image row before a storage with old files is taken
    for the wrong database;
  - more than 1000 orphans in one run are taken for a database that is another one, or
    an older copy (a restore): a crashed upload or a failed removal leaves a handful.
    The operator raises the limit for a run with `STORAGE_SWEEP_MAX_REMOVALS` after
    checking the database. (Until the stage review this was "at most 1000 a run, the
    rest waits": against a wrong database that removed 1000 files an hour.)
  The worker is stopped while a database is restored or replaced (backend.md).
- Temporary files of an interrupted write (`.upload-*`) are among the names we never
  generate: reported, left for a person to remove.

**Wardrobe**
- The list's cursor is an item id of the user's: the page continues after it (newest
  first, then by id). A cursor that is not one of the user's items gives an empty last
  page, as the old API did for an unknown id. Go is stricter in one case: the old API
  also took another user's item id as a position (the page held the caller's items
  only, either way); Go takes the caller's own items only.
- The list's cursor in another category of the user's gives its position (the items of
  the category after it); the old API's cursor (Prisma) dropped one more item there. No
  client sends such a cursor: it always comes from a page of the same list.
- A correction records each changed field (`from`, `to` as the old API wrote them, and
  the time), sets `wasCorrected`, and changes nothing when nothing differs. A change and
  its log entry are one statement. The rules are the old API's own functions
  (`apps/web/src/lib/wardrobe/corrections.ts`, taken out of the route unchanged), checked
  by golden vectors: the logged entries, their order, the columns written and the stored
  log to the byte.
- Corrections of one item go one at a time (the row is locked while it is compared and
  written), so two at once cannot lose each other's log entries, as they could in the
  old API. The time of a correction is the database clock.
- The id in the path is judged before the query and the body, trimmed, as the old API
  did; the session and the consent are still checked first.
- Deleting an item answers success once its rows are gone. Its files are removed after
  that, even when the client has left; files that cannot be removed are logged and left
  to the sweep (the old API removed them before answering, skipped a file it could not
  remove, and nothing removed that file later).
- A stored list, confidence object or correction log that is not the JSON it should be
  is an internal error, never shown as empty.
- Analysis in this stage: the development mock, ported exactly (colours from a 32×32
  resample of the pixels, the file-name hints, the confidences). `AI_VISION_PROVIDER`
  other than `mock` is refused at start until B6, and the mock is refused in production
  unless `AI_ALLOW_MOCK_IN_PRODUCTION=1` (the Next.js rule).

**Limits** (owner decision, 2026-11-26: 100 a day, 1000 items)
- Uploads: 100 per user per Tashkent day. The count lives in the rate limiter, with the
  day in its subject. A replay is not counted.
- Items: at most 1000 per user, checked before any work and again under the user's lock
  in the transaction that creates the item.
- The order of an upload that holds its idempotency claim (settled in the stage review):
  the picture's header (format, dimensions), then the wardrobe's size, then the day's
  count, then the processing. So a file we do not take is told so even at the limit
  (HEIC at the 101st upload answers 415, not "come back tomorrow"), and is never counted.
- A failed upload gives its attempt back to the day, with one exception: a picture
  whose header passed and whose pixels could not be read stays counted. It took a
  processing slot; uncounted, a stream of such files would keep both slots busy at no
  cost to the sender.
- Codes (corrected while building B4.5: this file first named `RATE_LIMITED` for both,
  which the contract does not list for the upload). No contract change:
  - the daily limit answers `AI_QUOTA_EXCEEDED` (429) with `Retry-After` up to the next
    Tashkent midnight and its own message. The contract lists it for the upload with
    that header, and the apps tell the user what is true: today's limit is used up
    and renews at midnight. (The mobile app's own text for this code named the AI
    quota's number, "kuniga 50 ta"; it now names no number: the server decides it.)
    The glossary's "Quota" means AI calls; this code is used for the upload limit
    because it is the one the contract and the apps already understand here;
  - a full wardrobe answers `VALIDATION_ERROR` (400) with the message "Garderobingizda
    1000 ta kiyim bor. Yangisini qo‘shish uchun avval keraksizlarini o‘chiring." (the
    glossary's words; the numbers in both messages come from the limits). The
    apps show a validation error's own message, so the user reads what to do; with
    `AI_QUOTA_EXCEEDED` they would be told to wait for midnight, which would not help.
    A code of its own is a contract change for a later stage, with the app update that
    understands it.

**Upload**
- The request is judged in the old API's order: session and consent, the
  `Idempotency-Key`, the declared length (required; 10 MB), the form, the file, its
  declared type, its size (8 MB), then the bytes. A part with a file name is a file;
  the form's first `file` must be one. The form's type must be `multipart/form-data`
  itself (a type that only starts so is a bad form, as in the old API).
- The request's identity (the idempotency hash) is the old API's: the picture, its
  name, and the text fields but those named `file`, of a repeated one the last. Names
  are read as the Fetch API reads them (`%22`, `%0A`, `%0D` are a quote and the line
  ends). The mock's hint is the form's first `filename` when that is text. A part
  without a name, or one that is not `form-data`, is a bad form. Go's reader takes some
  spellings of a part's header the old API refused as a bad form (an unquoted name, a
  backslash-escaped quote, `filename*`, no space after the semicolon); no client of
  ours writes them.
- Uploads in flight are bounded before a body is read, because an upload holds its
  picture in memory until it is answered: two of one user, sixteen in all. One more
  answers `AI_UNAVAILABLE` with `Retry-After: 15` and "Server hozir band. Birozdan so‘ng
  qayta urinib ko‘ring." The old API had no such bound.
- The upload route has its own budget: a 10 MB body and 90 seconds (receiving from a
  phone on a slow connection, waiting for a processing slot, processing), with the
  server's read and write deadlines moved to match. Every other route keeps 64 KB and
  30 seconds.
- When the picture cannot be processed within that time (both slots busy throughout),
  or the request ends first, the answer is `AI_UNAVAILABLE` with `Retry-After: 15` and
  the same message: nothing was stored or counted, and the apps keep the upload for a
  retry with the same key. The old API had no such limit.
- Once the files are stored, the transaction that creates the rows runs to its end
  whatever becomes of the request (its own 10 seconds): a client that left learns of
  the item from its retry, never of a failure that may or may not have happened.
- An account deleted while its upload runs: nothing is created, the files are removed,
  the answer is `UNAUTHORIZED`.
- A request whose key was taken over while it ran (it ran for five minutes) answers
  `IDEMPOTENCY_IN_PROGRESS`; the old API answered an internal error there.
- The stored row is the old API's: the mock's provider, model and version, the
  confidences as JSON in the mock's order, the uploaded bytes' size and SHA-256.
- `AI_VISION_PROVIDER` must be `mock` (or unset outside production and staging) until
  B6; in production and staging the mock needs `AI_ALLOW_MOCK_IN_PRODUCTION=1`, as in
  the old API.

**Found while building, and fixed here**
- The image rows had no index on their item, and outfit entries none on their outfit
  or item: every wardrobe list and read, and every deletion (the cascade), read the
  whole table. Prisma migration `20261126000000_wardrobe_child_indexes` adds the three
  indexes (with its rollback script and the rollback tests' chain); the Go baseline is
  rebuilt. Running it in production is a deployment step with the owner's go-ahead.
- The Go server sent none of the headers the Next.js server sends with every response
  (`nosniff`, `X-Frame-Options: DENY`, the referrer policy, `frame-ancestors 'none'`):
  a gap since B2, unseen because Go mode ran a chosen list of browser specs and the
  header spec was not on it. The headers are now set for every answer of the Go server,
  and CI runs the whole browser suite in Go mode.

**Owner decision, 2026-11-26**: the `r2` driver is first run against a staging bucket
of the owner's Cloudflare account, when that account exists (not against another
S3-compatible server in CI). Until then it stays "not verified against a real service".

## Contract impact

None. Both limits answer with codes the contract already lists for the upload (see
Decisions, Limits).

## Testing

Seam: the HTTP handlers over the real router, gate and PostgreSQL; image processing on
generated images and fixtures; the local driver on a temporary directory; the `r2`
driver against AWS's documented signature examples and a stand-in service in the tests
that verifies each request's signature and payload hash.

Changed while building B4.6: the plan named MinIO as the real S3-compatible server for
the `r2` tests. MinIO's server was archived and is no longer distributed, and no other
server could be installed in the build session. **The `r2` driver has not run against
a real S3-compatible service yet**; that run is against a staging R2 bucket of the
owner's Cloudflare account, when the account exists (owner decision above, ADR 0010).

- Body, query and header rules: every golden case.
- Catalog: equal to the TypeScript one.
- Signed URLs: golden vectors (sign and verify), expiry, tampering, key pattern.
- Images: each accepted format (with alpha, 16-bit PNG, progressive JPEG), every EXIF
  orientation 1–8 (result upright, width and height swapped for 5–8), HEIC/AVIF brands,
  garbage, truncated files, dimension and pixel limits at and past their boundaries,
  metadata gone from every variant, variant sizes; fuzzing of the decoders' entry.
- Mock vision: golden vectors from the TypeScript mock on solid and two-colour images,
  and the file-name hints.
- Upload: success, each refusal above with nothing stored (no row, no file), idempotent
  replay, mismatch, in progress, takeover after 5 minutes; the limits (100th and 101st
  upload, Tashkent midnight, 1000th and 1001st item, concurrent uploads at the limit).
- List, read, correct, delete: ownership (another user's item is `NOT_FOUND`), pages and
  cursors, the correction log, files removed.
- Media: served with its headers, 404 for every bad link, from both drivers.
- Sweep: orphans older than the minimum age removed, recent ones and referenced ones
  kept, unknown names reported; nothing removed for an empty database or over the
  limit; a file named since it was listed kept.
- Config: every storage and vision rule, fail closed, secrets not printed.
- e2e: the whole browser suite passes in Go mode with the wardrobe and media operations
  answered by Go (`go-mode.spec.ts` proves the routing).

## Security gate (lookly-security, 2026-11-26)

B4 touched uploads and stored files, signed media links, per-user limits, a storage
service's credentials (`R2_SECRET_ACCESS_KEY`), the link-signing secret, and CI.

Checklist "Uploads and media":
- The body is limited while it is read (`http.MaxBytesReader`, 10 MB for the upload,
  64 KB elsewhere), a declared length is required, and the picture is read up to 8 MB
  and one byte. Yes (tested; the connection is closed on an oversized body).
- The type is decided by the bytes; only JPEG, PNG and WebP; the declared type and the
  name decide nothing but an early refusal. Yes (tested with HEIC and GIF bytes sent
  as JPEG and PNG).
- Dimensions and pixel count are read from the header and refused before a pixel is
  decoded; a header that disagrees with the pixels is refused; decoding is bounded to
  two pictures at a time and uploads in flight to two a user and sixteen in all. Yes
  (tested; the fuzz test of the decoders' entry runs its seeds with every test run).
- No metadata in any stored variant, orientation applied first. Yes (tested on every
  fixture and all eight orientations).
- Per-user upload rate and storage cap: 100 a day, 1000 items (owner decision). Yes
  (tested at both boundaries and under concurrent uploads).
- Storage keys are made by the server (`users/<owner>/<uuid>…`) and checked against
  that pattern before a path or an object name is built, in both drivers and in the
  sweep. Yes (tested with traversal, encodings and links in place of directories).
