# B7 — Cutover: one backend, in Go

Started at `747665d` (2026-11-28). Owner decisions: ADR 0002 (one cutover), ADR 0012
(mobile app only; the website is a landing page), and of 2026-11-28: the user web
pages are kept in Git history, not in the code, so that a Telegram Mini App can start
from them later (the archive point is recorded below when they are removed).

## Problem

Two backends live in the repository: the Go server (B0–B6: every operation of the
contract) and the Next.js API with its server code and Prisma, which nothing in
production ever ran. Every change still has to keep both green (the contract is
generated from the TypeScript registry, Prisma owns the schema, the browser suite
drives the web pages over the Next.js server and the Go server through a test proxy).

## Solution

After B7 the repository has one backend: the Go server owns the API, the contract
document and the database schema; `apps/web` serves only the landing page (at `/`),
the legal pages, the page an e-mailed reset link opens, and later the admin panel,
and calls the Go API for anything it needs.

- **Tests first.** An API journey suite against the Go server (with its worker and a
  real PostgreSQL) takes over what the browser suite proves through the web pages,
  before those pages and the old API go.
- **Schema.** `lookly migrate` applies the Go migrations; on a database Prisma made it
  records the baseline as applied (ADR 0007). Prisma's history is frozen and removed.
- **Contract.** `docs/api/openapi.json` becomes hand-owned (ADR 0003): the TypeScript
  registry and its check go; the Go server and the Dart client are generated from the
  document and CI fails on drift, as today.
- **Evaluation.** The AI evaluation harness keeps its cases, scoring and reports and
  runs the Go pipeline only (`lookly eval`); the TypeScript pipeline it compared
  against goes with the old API.
- **Deployment.** One Compose project: PostgreSQL, the Go server, the Go worker, the
  web app, Caddy (`/api/*` to Go, everything else to the web app, security headers).
- **Staging.** The stack on the owner's VPS, the phone app pointed at it and checked
  by the owner. This last step waits for the VPS and the Cloudflare account.

Nothing has users or data, so there is no data migration and no mixed operation.

### B7.4 plan (from reading the harness)

The harness (`apps/web/scripts/ai-eval`, about 5,500 lines) imports `src/lib/ai` for
three things: types and catalog constants (cases, scoring), the TypeScript pipeline
itself (the runners, the scoring context, the bake-off's in-process providers, the
per-attempt accounting), and a few versions and checks (`real-data/*`). Slices, each
green:

| Slice | What |
|---|---|
| a | Freeze today's offline records (equal on both pipelines) as a golden file; a Go-only test compares against it from then on |
| b | `lookly eval` returns what scoring needs: `setup` (stylist refs, messages, schema; outfit candidates, weather and profile use, the deterministic explanation; vision picture size), a `dryRun` request (no call), per-attempt outcomes, `versions`, a `color` case; cases decoded strictly |
| c | The harness's own protocol types and stand-in provider interface; catalogs from `apps/api/internal/catalog/catalog.json` |
| d | Scoring, replay and the fallback explanations from Go's `setup` |
| e | Go-only runners; the TypeScript runners and `--pipeline` go; robustness through the stand-in |
| f | Accounting, circuit breaker and cost reservation per case on Go's results; the bake-off on Go |
| g | `real-data/*` on Go |
| h | `timings.ts` retired for Go benchmarks; a test that nothing in the harness imports `src/`; docs |

About 2,000–2,500 lines touched, about 1,000 of them deletions. Lost on the way: the
circuit breaker stops between cases, not inside one (still within the call cap), and the
cost reservation is per case (coarser, more conservative). One owner decision (rule 6):
two robustness expectations follow Go's documented behaviour on an answer that is not
JSON (B6.9).

**Owner decisions, 2026-11-28:** the harness is kept whole (plan A: bake-off, replay,
real-data tooling and live accounting move to Go too); the two robustness scenarios
on an answer that is not JSON expect Go's outcome (`error_malformed_response` for the
stylist, `fallback_error_malformed_response` for the outfit, one call each; applied in
slice e, when the scenarios run on Go only).

B7.4a done: `tests/eval-go/golden/offline.json` holds every offline record and request
(17 stylist and 11 outfit cases, 9 provider failures on each feature, the two
corrections, a case with preferences, 15 synthetic pictures, 13 robustness scenarios),
written by `scripts/ai-eval/golden-offline.ts` from the TypeScript pipeline (the same

pair-by-pair comparison is gone (only the process test of `GoPipeline` stays). Dropping
the preferences or the colour profile from what is sent to Go fails it.

B7.4b done: every `lookly eval` result carries `attempts` (each provider attempt's
outcome) and `setup` (what the case became before a model was asked: stylist
references, messages and schema; outfit candidates with references, signals and items,
weather and profile use, the deterministic explanation, messages and schema; the
prepared picture's size); `dryRun` makes the setup with no call; `versions` and a
`color` case are answered; cases are decoded strictly (an unknown member at any depth
is refused). Tested over the command (setup equals what the stand-in received, a dry
run sends nothing, attempts per case, the colour vectors an upload accepts, the
profile thresholds) and in the client (each attempt's outcome); the offline golden
stays green on both pipelines.
