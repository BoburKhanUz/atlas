# B2 — Auth and sessions

Started at `aa42fbf` (2026-11-25). Stage goal and exit criteria: `docs/plan/README.md`.
Binding: ADR 0001, 0002, 0003, 0007, 0008; `docs/architecture/sessions.md` (the session
protocol); `.claude/skills/lookly-go-backend/references/porting.md` (what to reproduce and
what not to copy); `.claude/skills/lookly-security/references/checklists.md` (sessions).

## Problem

The Go service has no way to know who is calling. Every endpoint after this stage needs
an authenticated user, a consent check and protection against cross-site requests.
Sign-in itself must behave exactly like the Next.js API, because the mobile app's session
recovery depends on the exact error codes, and because sessions written by one
implementation must be readable by the other until the cutover.

## Solution

The Go service serves `register`, `login`, `logout`, `getMe` and `refreshSession` with
the contract's responses, cookies and error codes, on the shared database, with the
session protocol of `docs/architecture/sessions.md`. Authenticated routes get one
middleware: Bearer token or cookie, session still alive, consent current, same-site for
cookie requests. The known defects of the old API are not carried over.

## User stories

1. As a new user, I want to register with email, password, the accepted legal version and
   the age confirmation, and be signed in at once.
2. As a user, I want to sign in with email and password. A wrong email and a wrong
   password give the same answer in about the same time.
3. As a mobile user, I want tokens in the response body and never cookies
   (`X-Atlas-Client: mobile`). As a web user, I want HttpOnly cookies and no tokens in
   the body.
4. As a user, I want my session refreshed without signing in again: a refresh rotates the
   token; a replay within 60 s gets the same successor; a replay after it ends the
   session family (`REFRESH_REUSED`).
5. As a user, I want sign-out to end the session at once: the access token stops working
   immediately, not after up to 15 minutes.
6. As a user, I want `GET /auth/me` to tell me who I am and whether I must accept new
   legal texts, even when my consent is out of date.
7. As a user whose consent is out of date, I want every other authenticated request
   refused with `CONSENT_REQUIRED`.
8. As a user, I want my account protected from password guessing, without one stranger
   being able to lock everybody out. (Someone who knows my email can still delay my own
   sign-in: ten wrong passwords close the account's window for up to 15 minutes. That is
   the price of the per-account limit; see Decisions.)
9. As a web user, I want cross-site requests that ride on my cookies refused.
10. As the operator, I want the server to refuse to start without valid session secrets.
11. As a user who registered under the old API, I want my password to keep working, and
    to be stored more strongly after my next sign-in, without noticing.

Unhappy paths, each with the contract's code:
- invalid body: `VALIDATION_ERROR` with the field;
- duplicate email, also when two registrations race: `CONFLICT`;
- wrong credentials: `UNAUTHORIZED` with the Node message;
- too many attempts: `RATE_LIMITED` with `Retry-After`;
- no or invalid token: `UNAUTHORIZED`;
- refresh outcomes as the protocol table: `INVALID_TOKEN`, `SESSION_EXPIRED`,
  `SESSION_REVOKED`, `REFRESH_REUSED`, `CLIENT_MISMATCH`, `SESSION_RACE`;
- lock contention: `SESSION_BUSY` (503, `Retry-After: 1`);
- a password over 72 bytes at registration: `VALIDATION_ERROR`.

## Decisions

- **Exact parity for everything stored or signed** (parity strength "exact"), so both
  implementations accept each other's sessions:
  - JWT: HS256, issuer `ai-fashion-stylist`, claims `sub`, `email`, `sid`; expiry capped
    by the family's absolute limit, in whole seconds.
  - Refresh token: 32 random bytes, base64url, stored as SHA-256 hex.
  - Successor ciphertext: `v1.<keyId>.<iv>.<ct>.<tag>`, AES-256-GCM, AAD
    `<rotatedId>|<successorId>`.
  - Cookies `atlas_at` and `atlas_rt`: Path `/`, HttpOnly, SameSite=Lax, Max-Age rounded
    up from the database clock.
  - Checked with golden vectors generated from the TypeScript code
    (`apps/api/testdata/golden/`). — default (parity.md).
- **Passwords** (owner-approved, 2026-11-25): bcrypt cost 12 for new hashes. A cost-10
  hash is replaced after a successful sign-in. A password over 72 bytes is refused when
  it is set (registration), never at sign-in.
- **Session checked on every request.** An access token is accepted only while its
  session row is alive (not revoked, family not revoked). The Node API accepted it until
  it expired. A request with a dead session answers `UNAUTHORIZED`; the clients then
  refresh and get the precise reason. — default (porting.md defect list).
- **Rate limits live in PostgreSQL**, per account and per IP, counted on failed attempts
  only, with no global bucket that lets a stranger lock everyone out:
  - sign-in: 10 failures per account and 50 per IP in 15 minutes (the Node numbers);
  - registration: 10 per IP per hour. Without a trusted IP (`TRUST_PROXY` unset), one
    shared bucket of 100 per hour, as today.
  - Keys are stored hashed (an email is personal data), with a key derived from the
    server's secret: plain SHA-256 of an address or a common email is reversed by
    guessing. A successful sign-in does not clear the count.
  - An attempt is counted before the password is checked and given back when the
    sign-in succeeds. Checking first and counting afterwards would let a burst of
    parallel requests through before any of them is counted.
  - Registration counts every attempt that passes validation, successful or not: a
    `CONFLICT` answer tells whether an email is registered, so probing is limited too.
  - The per-account limit means a stranger who knows an email can keep that one account
    from signing in (ten failures every 15 minutes). The alternatives (limit per account
    and address, with a higher ceiling per account) trade this against more guesses per
    day for an attacker with many addresses. Kept as specified; an owner decision if it
    is to change.
  - The table is added by a Prisma migration (`20261125000000_rate_limit_bucket`), and
    the Go baseline is rebuilt (ADR 0007: Prisma owns the schema until B7). As every
    migration here, it ships its rollback script
    (`docs/database/rollback/down-rate-limit-bucket.sql`), now the first in the rollback
    order; the rollback tests cover it.
  - Expired rows are removed by the hourly cleanup. — default.
- **Registration is one transaction** (user, profile, preferences, consent). A unique
  violation is `CONFLICT`, not 500. — default (porting.md).
- **Legal versions** (`LEGAL_VERSION`, minimum consent version) are constants in Go, with
  a test that they equal the TypeScript ones until B7. The legal texts and
  `POST /legal/consent` are B3. — default.
- **CSRF** as the Next.js proxy does it. A state-changing request that carries a session
  cookie, has no `Authorization` header and comes from another origin is refused with
  `FORBIDDEN`; an `Origin` of `null` counts as another origin; a missing `Origin` passes.
  — default.
- **Configuration** keeps the shared names: `JWT_SECRET`, `SESSION_ENC_KEY`,
  `SESSION_ENC_DECRYPT_KEYS`, `ACCESS_TOKEN_TTL_SECONDS`, `REFRESH_TOKEN_TTL_DAYS`,
  `COOKIE_SECURE`, `TRUST_PROXY`. The same rules apply: minimum lengths, known insecure
  defaults refused, keys independent of each other. In production (`LOOKLY_ENV`)
  `COOKIE_SECURE=0` is refused: the plain-http e2e and local runs use the test or
  development environment. — default.
- **E2E before the cutover.** The Playwright specs drive Next.js pages. In "Go mode" a
  test-only front proxy sends the five auth operations to the Go server and everything
  else to Next.js, on one database with the same secrets. This is a test arrangement
  only; production still switches in one step (ADR 0002). — default.

- **Where Go is stricter than the TypeScript code** (found by the golden vectors, each
  listed by name in the tests; none is something either signer produces):
  - an access token without `exp`, with an empty `sub`, with padding or stray bits in
    its base64url, or with characters around it, is refused;
  - only spaces and tabs separate `Bearer` from the token;
  - a successor ciphertext is read only in its canonical form;
  - a session setting that is malformed or out of range stops the server, where the
    Next.js server used the default or the nearest limit;
  - an `Origin` in a spelling no browser sends (a port with leading zeros, backslashes)
    is another site, where JavaScript's URL parser would normalise it to ours;
  - a forwarded client "address" that is not an address is not used for rate limits;
  - the `X-Atlas-Client` header sent twice is refused by the generated router
    (`VALIDATION_ERROR`); the Next.js API read it as web mode.
  — default (fail closed; no client depends on the lenient forms).
- **Request validation is an exact port**, messages included: the Next.js validator
  answers in Uzbek, and a user must read the same text from either server. One
  simplification: for a member of the wrong type the Next.js validator also reported
  length problems of arrays (and of objects with a `length` member); Go reports the
  wrong type only. — default.
- **A rotated session's access token stays valid** until it expires, while its family
  stands. Refusing it the moment its session is rotated would fail requests that are in
  flight during a refresh. What ends a family (sign-out, reuse, expiry, password reset,
  account deletion) ends its access tokens at once. — default.
- **A token without a session id is refused.** Only tokens from before the session
  protocol lack it, and those expired long ago. — default.

## Contract impact

None. Every response, header and code is already in the contract, with one gap found
while porting, which both servers share and which B2 leaves as it is: the cross-site
guard can answer `403 FORBIDDEN` on register, login and refresh, and starting a session
can answer `503 SESSION_BUSY` on register and login, but the contract lists neither for
those operations (it lists `FORBIDDEN` only where a session is required). The Go tests
name these five answers and check their bodies against the error schema. Documenting
them is a change to the contract's generator (`registry.ts`) and a regeneration of the
mobile client; it is proposed for the stage review, not done silently here.

Two behaviours are stricter within the contract: a dead session's access token
(`UNAUTHORIZED`), and a password over 72 bytes at registration (`VALIDATION_ERROR`; the
contract allows up to 200 characters, the server refuses long ones with a clear Uzbek
message).

## Testing

- Seams: HTTP through the real router for every operation, with responses validated
  against the contract; the session protocol against a real PostgreSQL with the settable
  database clock; pure functions (classification, tokens, crypto) with golden vectors.
- Golden vectors from the TypeScript code: JWT signing and verification (including
  `alg: none` and a wrong issuer refused), refresh-token hashing, successor encryption in
  both directions, `classifyRefresh` over every boundary (60 000 and 60 001 ms, the
  absolute limit, legacy rows), cookie attributes and Max-Age.
- The protocol, ported from `session-protocol.itest.ts` case by case (rotation, every
  boundary, grace replay, reuse, family stamping, access-token expiry capped by the
  family, legacy rows, key rotation with decrypt-only keys, forced lock contention giving
  `SESSION_BUSY`), plus the two cases the B1 review named: a session deleted by a
  concurrent cleanup is `INVALID_TOKEN`; a replay whose ciphertext was cleared fails
  closed as `SESSION_RACE`.
- HTTP, ported from `session-http.itest.ts` and the regression tests: web and mobile
  modes for all five operations, cookies set and cleared on exactly the documented codes,
  an `Authorization` header never falling back to cookies, CSRF cases, consent gate and
  its exemptions, a dead session refused at once.
- Passwords: a cost-10 hash still signs in and is re-hashed at cost 12; 72 bytes accepted
  and 73 refused at registration (multi-byte characters counted in bytes); a long
  password is not refused at sign-in.
- Rate limits: the 10th failure passes and the 11th is `RATE_LIMITED` with `Retry-After`;
  successes are not counted; another account and another IP are unaffected; the window
  ends on the database clock; the stored key is not the email.
- Registration: two concurrent registrations of one email give one 201 and one 409, and
  no partial rows.
- Timing: sign-in with an unknown email performs a password comparison (asserted through
  the hasher seam, not by measuring time).
- The 9 client-recovery vectors: for each, the server produces the listed refresh
  responses in the listed situations (`docs/api/client-recovery-vectors.json`).
- E2E in Go mode: `auth.spec`, `session.spec` and `session-recovery.spec` pass with the
  five operations served by Go, including sessions created by one implementation and
  rotated by the other. Run in CI.
- Fuzzing (testing skill): the Bearer and cookie parsing, the JWT verifier and the
  successor-ciphertext decoder never panic and never accept a mutated token.
- Configuration: each new variable's refusals, as in B0.

## Out of scope

- Password reset, `POST /legal/consent`, legal documents, profile and account deletion
  (B3). The functions they need from sessions (`revokeUserFamilies`, the session
  transaction) are built here.
- The web pages calling Go (W1, with B7) and the Next.js page proxy.
- Admin roles (B8), device lists and "sign out everywhere".
- Email verification and sign-in by phone number with an SMS code. The owner asked for
  both on 2026-11-25, with a provider-neutral SMS sender, and chose to add them after
  the cutover: stage B9 (and M8 for the screens). B2 stays an exact port. It adds no
  placeholder for them; the account identifier is not assumed to be an email outside
  the sign-in and registration code itself.
- Schema improvements (indexes, jsonb): B7.
