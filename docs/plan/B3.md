# B3 — Profile, consent, password reset, mail, account deletion

Started at `7f169e8` (2026-11-26). Stage goal and exit criteria: `docs/plan/README.md`.
Binding: ADR 0001, 0002, 0003, 0007, 0008; `docs/architecture/sessions.md` (lock order);
`docs/plan/B2.md` ("Notes for B3");
`.claude/skills/lookly-go-backend/references/porting.md`;
`.claude/skills/lookly-security/references/checklists.md` (sessions, quotas, secrets).

## Problem

The Go service can sign a user in, and nothing more. The account's own pages still
depend on the Next.js API: the profile and style preferences, the legal texts and the
renewed consent, the password reset by e-mail, and the deletion of the account. Two of
them need things the Go service does not have yet: a way to send e-mail and a way to
remove a user's stored images.

## Solution

The Go service serves `getProfile`, `updateProfile`, `getLegalDocuments`,
`acceptLegalDocuments`, `requestPasswordReset`, `resetPassword` and `deleteAccount` with
the contract's responses and error codes, on the shared database. E-mail is sent by the
worker, through SMTP or (development and tests) into an outbox directory in the format
the Next.js server writes. Deleting an account removes its rows in one transaction and
its images by a background job that is retried until it succeeds.

## User stories

1. As a user, I want to see my profile and style preferences.
2. As a user, I want to change my name, profile fields and preferences; a request that
   changes several of them changes all or none.
3. As anyone, I want to read the current privacy policy and terms of use with their
   version, without signing in.
4. As a user whose consent is out of date, I want to accept the current texts and use
   the app again at once.
5. As a user who forgot the password, I want a one-time link by e-mail. The answer is the
   same, after the same work, whether or not the address has an account.
6. As a user with a link, I want to set a new password; every device is signed out, the
   link works once and for 60 minutes, and a newer link replaces the older ones.
7. As a user, I want to delete my account: my data is gone at once, my sessions stop
   working at once, and my images are removed even if the server restarts meanwhile.
8. As a user whose consent is out of date, I can still delete my account.
9. As the operator, I want the server to refuse to start with incomplete mail or storage
   settings, and never to send credentials or links over an unencrypted connection to a
   remote mail server.
10. As the operator, I want no e-mail address, link or token in logs or in the job queue.

Unhappy paths, each with the contract's code:
- invalid body: `VALIDATION_ERROR` with the field (the Next.js messages);
- mail not configured: `PASSWORD_RESET_UNAVAILABLE` (503) on the request for a link;
- too many requests: `RATE_LIMITED` with `Retry-After`;
- unknown, used or expired link: `RESET_TOKEN_INVALID`, and nothing changes;
- new password longer than 72 bytes: `VALIDATION_ERROR` (as at registration);
- reset while the account's sessions are locked too long: `SESSION_BUSY`, `Retry-After: 1`;
- no session: `UNAUTHORIZED`; consent out of date on the profile: `CONSENT_REQUIRED`;
- the account disappeared while the request ran: `NOT_FOUND` where the contract lists it
  (profile read, account deletion), `UNAUTHORIZED` elsewhere (profile change, consent);
- the mail server refuses or is down: the job is retried, then dropped with a log entry;
  the user asks again.

## Decisions

Each is a default (decided here, not by the owner) unless marked.

**Request rules**
- The four request bodies are judged as the Next.js schemas judge them: same fields
  reported, same order, same messages (golden vectors from the real schemas). Text is
  trimmed where the schema trims; `null` and "absent" stay different where the schema
  distinguishes them. Unknown members are ignored. As in B2, for a member of the wrong
  type only the wrong type is reported.
- Numbers: `height` and `weight` are any finite number in range; `typicalBudget` is a
  whole number. A number too large for a double (the old server reads it as infinity and
  refuses it) is refused as out of range.

**Profile**
- A change is one transaction: user name, profile row and preferences row together
  (the old API wrote them one by one — porting.md, defects).
- A section that is present updates its row's `updatedAt`, also when it is empty (`{}`),
  and creates the row when a user from before the rows were made at registration has
  none.
- Stored style and colour lists stay JSON text until B7. Text that is not a JSON list of
  strings is a server error with the cause logged; it is not served as an empty list
  (only this server writes the column, from validated values).
- The responses keep the two shapes of the old API: the read returns the rows and the
  preferences with lists; the change returns the user with the raw rows (lists as JSON
  text). The mobile app and the web read both.

**Legal texts and consent**
- The texts are owned by `apps/web` until the cutover. The Go service embeds a JSON copy
  generated from them; a test in each app fails when the copy and the source differ.
- Accepting records one row per user and version: the user's row is locked while the
  check and the insert run, so two requests at once cannot both insert. With that, the
  consent check reads at most the 20 newest rows of a user (B2 note).
- Accepting for an account that no longer exists is `UNAUTHORIZED` (as the old API).

**Password reset**
- Request: the handler looks the address up and always puts one job into the queue,
  carrying the user id or nothing. The same work is done for a known and an unknown
  address, and no e-mail address enters the queue.
- The job (worker) makes the token, sends the message and, once it has left, ends the
  user's earlier links (the old API ended them before sending). A message that does not
  leave leaves no new link behind, and the earlier ones stay as they were. Only links
  made before the sent one are ended: two jobs for one account at the same time leave
  the newer link standing, whichever message leaves first. Retried up to 4 times; a
  request older than 30 minutes is dropped: the user has asked again by then.
- Limits: 3 per hour per address of the mailbox (counted for every address alike),
  10 per hour per client address for a request, 20 per hour per client address for a
  reset. When the client address is unknown (no trusted proxy) one shared limit applies
  instead: 200 and 300 per hour, the old API's numbers. The old API's global limit on top
  of the per-client one is not copied: a handful of clients could close password reset
  for everybody (porting.md, defects; same reasoning as B2).
- Only requests with a valid body are counted (the gate judges the body first, as in B2).
- The new password is hashed before the transaction, also for a wrong token (as the old
  API): the transaction stays short. The per-client limit bounds that work.
- Reset is one session-protocol transaction: the user's session families are locked
  first (the lock order of `docs/architecture/sessions.md`; the old API took the user's
  row first, which can deadlock with a refresh in flight), then the user's row, then the
  token's; new hash, the user's links deleted, every live family revoked
  (`password_reset`).
- What changes an account locks the user's row `FOR NO KEY UPDATE`: such changes go one
  at a time, and a session being created for the user (its foreign key) is not held up.

**Mail**
- Standard library only (`net/smtp`, `mime/*`): no new dependency.
- `MAIL_TRANSPORT`: `smtp`, `outbox` or `disabled`. Unset means `disabled` in production
  and staging and `outbox` in development and test. `outbox` is refused in production and
  staging (the Next.js override `MAIL_ALLOW_OUTBOX_IN_PRODUCTION` exists for its e2e
  build; the Go e2e run uses `LOOKLY_ENV=test`).
- SMTP settings as the Next.js server reads them (`SMTP_HOST`, `SMTP_PORT`, `SMTP_SECURE`,
  `SMTP_USER`, `SMTP_PASSWORD`, `MAIL_FROM`, `PUBLIC_BASE_URL`). TLS from the first byte
  when `SMTP_SECURE` (default on port 465); otherwise STARTTLS, required unless the
  server is on localhost. Credentials are sent only over TLS or to localhost. TLS 1.2 or
  newer, certificate verified. Stricter than the old server: `MAIL_FROM` must also parse
  as an RFC 5322 address, and `PUBLIC_BASE_URL` is required for SMTP in staging too.
- The message is the old one, byte for byte (golden vector): subject, text and HTML.
- Outbox files keep the old format (`from`, `to`, `subject`, `text`, `html`,
  `createdAt`; one JSON file per message, mode 0600, directory 0700).
- Recipients, subjects and bodies are never logged.

**Account deletion**
- One session-protocol transaction: the user's session families are locked in id order
  first (the lock order of `docs/architecture/sessions.md`: a refresh in flight finishes
  before the deletion instead of deadlocking with it), the job that removes the images
  is put into the queue, and the user row is deleted (the schema cascades to everything
  the user owns; a test walks the foreign keys). The job exists if and only if the
  deletion commits.
- Too busy to get the locks: `SESSION_BUSY` (503, `Retry-After: 1`), as the other
  session-protocol operations answer. The contract does not list it for this operation
  (see Contract impact).
- Images: the job calls the storage driver's "delete everything of this owner". B3
  brings the local driver's part of it (the directory `users/<id>` under
  `STORAGE_LOCAL_DIR`); the R2 driver arrives with B4 behind the same interface.
  `STORAGE_LOCAL_DIR` has no default in the Go service and must be an existing absolute
  directory: a wrong default would "delete" nothing without anyone noticing.
  `STORAGE_DRIVER` is `local` or unset; anything else stops the server.
- Signing in while the account is being deleted: the session cannot be created for a
  user that is gone; the answer is the usual `UNAUTHORIZED` for wrong credentials.
- No password re-entry, confirmation e-mail or grace period: the contract has none, and
  the apps confirm in their own dialog (see Out of scope).

**Process**
- `lookly serve` puts jobs into the queue and so needs River's tables
  (`lookly migrate river`). It still starts without them (and without the database);
  until they exist the two operations that need the queue answer 500, and the log says
  what to run. (`lookly worker` refuses to start without them, as before.)

## Contract impact

None: no change to `docs/api/openapi.json`. Known gaps, named in the Go tests' list
(`knownContractGaps`) and left for a contract change (mobile client regeneration) in a
later stage or by the owner's decision:
- carried from B2: the cross-site refusal (403 `FORBIDDEN`) is not listed for the public
  write operations; here that adds `requestPasswordReset` and `resetPassword`;
- new: `deleteAccount` can answer 503 `SESSION_BUSY`, which the contract does not list
  for it. Clients treat an unlisted 5xx as "try again", which is what it means.

## Testing

Seam: the HTTP handler over the real router, gate and PostgreSQL; the worker's jobs
through River's own test path; mail through a fake SMTP server in the test and the
outbox directory; storage on a temporary directory.

- Body rules: every golden case of the four schemas (wrong types, limits, trimming,
  `null` against absent, unknown members, numbers at and past the limits).
- Legal: the bundle equals the source texts; public; validated against the contract.
- Consent: accept ends `CONSENT_REQUIRED`; repeat adds no row; two at once add one row;
  wrong version and unconfirmed age refused; no session refused; deleted account 401.
- Profile: read after registration; change of each section; several sections at once;
  a failing section changes nothing; `null` clears a field; rows created for a legacy
  user; malformed stored list is a 500; consent gate applies.
- Password reset request: same answer and one job for known and unknown addresses; no
  address in the queue; mail disabled 503; each limit with `Retry-After`; cross-site
  write refused.
- Job: token stored as a hash only, earlier links ended once the new one has left,
  message equals the golden one, link works; unknown user id does nothing; stale job
  dropped; a failing sender is an error (retry), leaves no new link and keeps the
  earlier one.
- Reset: new password works and the old one does not; every family revoked, access
  tokens dead; token single-use; expired token; unknown token; password over 72 bytes;
  password hash is bcrypt cost 12; concurrent resets with one token: one wins.
- Mail: SMTP with STARTTLS and with implicit TLS, with and without credentials; refusal
  to send without TLS to a remote host; refusal when the server rejects; header
  injection attempt in an address; outbox file format and permissions.
- Deletion: rows gone (every table that references the user), sessions dead at once,
  job queued in the same transaction (rolled back together), images directory removed
  by the job, other users' images untouched, odd owner ids refused, allowed with
  outdated consent, second delete 401.
- Config: every mail and storage rule, fail closed, secrets not printed.
- e2e: `password-reset.spec.ts` and `reconsent.spec.ts` pass in Go mode, with the
  profile, legal, consent, password and account operations answered by Go.

## Out of scope

- Password re-entry or a grace period for account deletion; changing a password while
  signed in; changing the e-mail address. Contract changes, for the owner to decide.
- Email verification and phone sign-in (B9).
- The R2 storage driver, uploads and media (B4).
- The contract gap above.
- Mail templates beyond the password reset message; a mail provider's HTTP API.
