| B4 | Wardrobe and media, R2 driver, upload limits (spec `B4.md`; started at `2b1ed74`, **done** 2026-11-27: review and security gate in `B4.md`; limits 100 uploads a day and 1000 items: owner decision 2026-11-26; the `r2` driver still to be run against a staging bucket of the owner's) | Wardrobe e2e specs pass; refusal paths tested |

| B6 | AI: providers, vision, stylist, colour profile, monitoring, `eval` command (spec `B6.md`; started at `f1cded3`, **done** 2026-11-28: review, security gate and live smoke in `B6.md`; AI calls stay in the request: ADR 0011; the colour analysis limited to 10 a day; production on OpenAI only, owner decision 2026-11-27) | AI e2e specs pass with mock providers; offline evaluation tests pass against Go |
| B7 | Cutover: Go serves the apps, Prisma retired, old API removed. The user web pages are retired, not ported (owner decision 2026-11-28, ADR 0012: mobile app only); their journeys move to API-level specs against Go | All browser and API specs green against Go; phone checked on staging |
| B8 | Admin API, with the landing page's settings (store links, owner decision 2026-11-28) and a public endpoint the landing page reads them from | Admin role enforced (tested); actions audited |
| B9 | Sign-up and sign-in (owner decision, 2026-11-25; after the cutover, so it is written once, in Go): email verification by a code sent at registration; sign-in with a phone number and an SMS code. The SMS sender is an interface with one adapter per provider, chosen by configuration, so providers can be swapped without touching the sign-in code. Also (owner decisions, 2026-11-27): the birth date is optional at registration and stored in the profile (a new `birthDate` column, Prisma migration per ADR 0007); a user who skips it sees it among the profile's steps still to fill in, with the other profile data (gender, height, and so on) asked later in the profile, not at sign-up. No minimum age and no "I am 18 or older" box. Consequences: Gemini's terms forbid apps likely to be used by people under 18, so production uses OpenAI only; OpenAI's terms (Services Agreement 3.3(c)) forbid letting minors use it without a parent's or guardian's consent, so the consent at registration covers that (proposed wording put to the owner: "if I am under 18, my parent or guardian agrees"); counsel checks it against Uzbek law and the privacy policy names the new data. Owner answers of 2026-11-28: a new password (sign-up, reset, change) needs at least 8 characters with a letter and a digit, existing passwords keep working; SMS goes to Uzbek numbers (+998) only at first; the minors' consent wording stays in the sign-up box as the default until counsel confirms or rewords it. An AI provider is given the age range only, never the date; the stylist and outfit prompts using it are a prompt change (owner approval, rule 6). Also: changing the password while signed in (the current password asked), and the password reset by an email code instead of a link, so it is done inside the app. Needs a contract change, the mail sender from B3, an SMS provider account (owner), and per-number and per-IP limits before SMS is enabled (each message costs money) | Contract and clients updated; a fake SMS adapter in tests and at least one real adapter checked on staging with the owner's approval; abuse limits tested; the app's screens (see M8) |
| B10 | Server texts in three languages (needed by M3; after the cutover, so it is written once, in Go): the server answers in the language the app asks for (`Accept-Language`: uz, en, ru; Uzbek otherwise) for error messages, catalog labels, outfit explanations, weather words and emails; the user's language is stored in the profile (emails use it); `GET` of the country of the caller's address, from a GeoIP database kept on the server (no outside service is asked; the address is not stored or logged). Legal texts in English and Russian need a translation the owner provides (a lawyer's, not a machine's). The stylist's and the outfit explanation's AI prompts in English and Russian are new prompts: owner approval and an evaluation run first (rule 6) | Contract updated; each text has all three languages (test); the stored language read and changed through the profile; the country lookup tested with fixed addresses and with no database; prompts approved and evaluated |
| B11 | Subscriptions (owner decisions, 2026-11-28): freemium, with Premium as a monthly and a yearly subscription; prices and what each tier gets are set by the owner (in the admin panel). Free and Premium differ by the daily AI limits (the quotas of B6 become per tier) and by features the owner names. Purchases go through Google Play Billing and Apple's in-app purchase (store rules for digital features); the server checks each purchase with the store and keeps the subscription's state (active, renewed, expired, refunded) from the stores' server notifications. Not in this stage: payment through Payme or Click (store rules), ads (owner decision: no ads in the app), shop partnerships and commission (owner decision: later, when a marketplace is added), a paid account for professional stylists (an idea, not planned) | Tiers and limits from the admin panel (tested); purchase verification against the stores' sandboxes; expiry and refund take Premium away (tested); the app's paywall and restore-purchase screens; checked on a real device with test accounts before the store submission (M7) |

## Mobile (Flutter, `apps/mobile`)

| Stage | Goal | Exit criteria |
|---|---|---|
| M1 | Fix the audited defects (2 high, 7 medium, 2 low) — details in `M1.md`; started at `523e6af`, **done** 2026-11-25 (review, re-review and security gate recorded in `M1.md`) | Each defect has a failing-then-passing test |
| M2 | Structure: shared code to `core`, no cross-feature imports, logic out of widgets, domain models | Cross-feature import check in CI; all tests green |
| M3 | Localization in three languages (owner decision, 2026-11-27): Uzbek, English, Russian. `gen_l10n`, every user-facing string to ARB in all three, Material and Cupertino localizations for each (Uzbek ones written for the system widgets Flutter has no Uzbek for). The language is proposed automatically: the phone's language when it is one of the three, else the country of the user's address (looked up by the server, see B10: Uzbekistan gives Uzbek; Russia, Kazakhstan, Kyrgyzstan, Tajikistan and Belarus give Russian; other countries English), else Uzbek. Without a network the phone's language or Uzbek is used. The first screen of a new install (before sign-in or sign-up) shows the three languages with the proposed one already chosen, so one tap continues; the user can change the language later in the profile (owner decisions, 2026-11-27). The choice is kept on the phone and, once signed in, in the user's profile on the server (B10), so that emails come in it too. The app sends its language to the server (`Accept-Language`) | No literal user-facing strings (CI check); every key present in all three ARB files (CI check); widget tests of the choice rules (phone language, country, neither, no network), of the first-launch language screen and of the change in the profile; main screens checked in each language at text scale 2.0 (Russian and English run longer); the language screen built to a design the owner approves (the owner's mockup: `apps/mobile/design/m3-language-screen.jpg`, see `apps/mobile/design/README.md`) |
| M4 | Design system: dark theme tokens, haptics, transitions, text scale to 2.0, portrait lock | Golden tests: main screens light and dark, 360dp, text scale 1.0 and 2.0 |
| M5 | Screens redesigned from the approved mockups (the owner brings mockups made with ChatGPT; references in `apps/mobile/design/`). New screens here (owner request, 2026-11-27): intro slides after the language screen (three, skippable); "About and help" in the profile (app version, contact, terms and privacy) | Owner approves each screen |
| M6 | Device testing: `integration_test/`, Android device, iPhone via TestFlight (macOS CI job) | Integration tests pass on both platforms |
| M7 | Release readiness, with an "update the app" screen (owner request, 2026-11-27): the server names the oldest app version it still serves, and an older app shows the screen with a link to its store instead of failing | `lookly-release` checklist complete; the update screen tested with a version below and at the minimum |
| M8 | Screens for B9: the optional birth date at registration (a date picker, skippable) and as a step of the profile's progress; enter the email code after registration; sign in with a phone number and an SMS code (resend timer, wrong and expired code, no network); change the password in the profile; reset a forgotten password by an email code inside the app | Widget tests for each state; owner approves the screens |
