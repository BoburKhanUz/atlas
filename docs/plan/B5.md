# B5 — Weather, outfit engine, outfits

Stage of the Go backend (`docs/plan/README.md`). Started at `2b4ec7e` (2026-11-27).
Status: in progress.

## Problem

The Go server answers accounts, profile and wardrobe; "what do I wear today" is still
answered by the Next.js API: the current weather, the outfits made from the user's own
wardrobe, and the saved outfits with their feedback.

## Solution

Port the weather endpoint, the deterministic outfit engine and the outfit endpoints to
Go behind the same contract. The engine is pure (no database, clock or randomness) and
is ported to exact parity: the same wardrobe, context and seed give the same outfits,
scores, reasons and ids in both servers, proved by golden vectors generated from the
TypeScript engine. The optional AI reranking is B6; until then the Go server answers as
the Next.js server answers with the mock provider: the deterministic order and the
deterministic explanation, `fallback: true`.

## User stories

1. As a user, I want the weather where I am (temperature, rain, wind, UV) so that
   outfits fit the day.
2. As a user, I want up to five outfits from my own wardrobe for the weather and the
   occasion, each with its score, reasons and a short explanation.
3. As a user, I want "another option" (a seed) to give other outfits, and the same seed
   the same ones.
4. As a user, I want to save an outfit, list my outfits (all or saved), open one, rename
   it, mark it saved or not, and delete it.
5. As a user, I want my likes and dislikes of the last 30 days to shape the next outfits.
6. As a user with an empty or one-sided wardrobe, I want to be told what is missing
   instead of an error.
7. As the operator, I want the weather service asked at most once per place per half
   hour, never with more precision than about a kilometre, and a failure of it not to
   stop outfits from being made.

Unhappy paths, each with the contract's code:
- coordinates missing or out of range, a malformed body or id: `VALIDATION_ERROR` /
  `BAD_REQUEST` as the Next.js schemas answer (golden vectors);
- an outfit that is not the user's, or does not exist: `NOT_FOUND`;
- saving with an item that is not the user's: `FORBIDDEN`; with items that are no valid
  outfit (roles, composition, duplicates): `VALIDATION_ERROR` with the old messages;
- the weather service fails or answers nonsense: `INTERNAL` for the weather endpoint
  (the contract lists nothing else, see Decisions); for generation, outfits without
  weather;
- consent out of date: `CONSENT_REQUIRED`; no session: `UNAUTHORIZED`.

## Decisions

Each is a default (decided here, not by the owner) unless marked.

**Engine (exact parity)**
- The engine's tables (weights, thresholds, slot limits, style families, warmth and
  formality tables, reason labels) and the seasonal palettes are read into Go from a
  JSON copy generated from the TypeScript modules; a test in the web app fails when
  the copy is stale, and Go refuses to start with a copy of another engine version. The rules are ported by hand and held to the
  TypeScript engine by golden vectors: seeded random wardrobes and hand-made edge cases,
  with every field of the result compared, the unrounded scores bit for bit.
- JavaScript's arithmetic is reproduced where it differs from Go's: `Math.round` (half
  up), stable sorts, string order (UTF-16 code units), `String(number)` for the seed's
  hash, `indexOf` giving -1 for an unknown formality.
- The engine version (`outfit-engine-v2`) is a constant in Go too; the tables' copy
  carries it, so a change of rules in one server fails the other's test.

**Weather** (the defects listed in `lookly-go-backend/references/porting.md` are not
copied)
- One cached path: the endpoint and the generation both read the cache (`WeatherCache`,
  key = coordinates rounded to two decimals, 30 minutes) and ask the service only on a
  miss. The Next.js generation asked the service every time.
- The service gets the coordinates rounded to two decimals (about a kilometre), as now.
- An answer without the fields we need is a failure and is not cached; the Next.js
  server stored zeros for them.
- The chance of rain is the mean of the next six hours from the hour of the request,
  in the place's own time; the Next.js server took hours 00–05 of the day.
- A failure of the service answers `INTERNAL` (500) on the weather endpoint, as now: the
  contract lists no other code there. A code of its own is a contract change for a
  later stage. The failure is logged with its cause.
- `WEATHER_PROVIDER`: `open-meteo` (default) or `mock` (the fixed demo weather; refused
  in production and staging). Any other value stops the server; the Next.js server took
  every value but `mock` for the real service.
- The service is asked for two days of hours instead of one, so that the six hours
  ahead exist in the evening too. Hours without a number are left out of the mean; no
  number at all in the window is a failure.
- "Fields we need" are all of them: the time, temperature, felt temperature, humidity,
  weather code, wind, UV index and rain of the current weather, each a number within
  the range the API accepts in a client's weather snapshot (rain: 0 to 1000 mm). A
  weather code we do not know is "cloudy", as in the Next.js provider. The Uzbek labels
  are the Next.js provider's, byte for byte.
- Requests for one cell at the same time share one question to the service (in one
  process); the question goes on when the request that started it gives up, and its
  answer is cached.
- A cache row that is not a complete, sensible weather counts as no row and is replaced
  (the Next.js API's rows are read as they are; its zeros for missing fields cannot be
  told from real zeros and expire within the half hour).
- A weather that could not be written to the cache is still answered; the failure is
  logged.
- The place is in no log line and in no error: the address asked is cut out of the
  HTTP client's errors.
- Only a 200 is an answer and a redirect is not followed (the Next.js provider took
  any 2xx and followed redirects).
- The weather is asked inside the request, for at most five seconds (ten with the
  cache write, whoever waits): the answer is needed in the same response, so a
  background job would not serve it. A panic in a question is that question's error.

**Generation**
- Order of work and inputs as in the Next.js route: the user's items by id; profile,
  preferences and the stored colour profile; the client's weather snapshot, else the
  weather for the coordinates (only when the wardrobe is not empty), else none; the
  feedback of the last 30 days; the engine; the deterministic explanation.
- `fallback` is always true and the explanation always the deterministic one until B6.
- Stored lists that are not lists of texts count as empty here and are logged by row
  and column, without their value (the wardrobe endpoints answer an internal error for
  them; generation must not fail on one bad row). The Next.js route took only text
  that is no JSON for empty: any other JSON value (`null`, an object, a text) went to
  the engine as it was.
- Image links are the thumbnail (else the display variant, else the picture itself) of
  each item's primary image (else its first), signed as in B4.
- What is read of the database is read in one read-only transaction (one view of the
  wardrobe, the preferences and the feedback); the weather is asked outside it.
- Bounds: at most 2000 items of a wardrobe (twice what one may hold) and 2000
  (outfit, kind of feedback) pairs of the last 30 days are read.
- Feedback is read only of the user's own outfits and items, whatever rows exist: an
  outfit of another user, or another user's item in an outfit, counts for nothing. The
  colour profile is used only when it is the user's own.
- No body at all is "nothing asked" (an empty object), as the Next.js API reads it.

**Outfits**
- Responses keep the Next.js shapes, member by member, including the members of the
  database row that the contract allows but does not list (`userId`, `reasonsJson`, the
  weather as stored text after a write, `outfitId` and `createdAt` of an outfit's items,
  `userId` of a feedback). Answering only the contract's members was tried and taken
  back: a browser spec reads `reasonsJson` from the save's answer. Cutting the answers
  down to the contract is a contract change for a later stage.
- The list's images carry their dimensions (the Next.js list did not read them and
  answered null; the detail always had them).
- An outfit's items are read in the order they were saved in. The Next.js rows share
  one time and are told apart by Prisma's ids, which sort by time; ids made in Go do
  not, so each item of an outfit is stored a millisecond after the one before.
- An id in the path is trimmed before it is looked up, as the Next.js routes read ids;
  the gate judges it wherever `{id}` stands in the route (the feedback route ends in
  `/feedback`).
- The items of an outfit being saved are locked against removal until the outfit is
  stored (the Next.js route could fail with a broken reference in between).
- Stored reasons that are no list of texts, a stored weather that is no object, or a
  garment's stored colours or seasons that are no list are an internal error, as in
  the wardrobe routes (B4) and as `JSON.parse` failed in the Next.js routes. No stored
  weather (NULL or empty, rows of before it was stored) is an empty object.
- Saving validates as the Next.js route does, in its order: roles, duplicates, ownership
  (`FORBIDDEN`), role against the item's slot, composition. Score and reasons are stored
  as sent.
- The list stays the 50 newest (no cursor in the contract yet; paging is a contract
  change for a later stage).
- Feedback and the change of `isSaved` it implies are one transaction (two statements in
  the Next.js route).
- Deleting an outfit removes its items and feedback (cascade).
- `GET`, `PATCH` and `DELETE` on `/api/v1/outfits/generate` are read as an outfit named
  "generate" and answer `NOT_FOUND`; the Next.js server answered 405 there.
- Feedback locks the outfit's row before it reads whether the outfit is saved, so what
  it does follows from the row as it is, not as it was.

**Limits** (decided here on 2026-11-27, because the security checklist asks for them;
the owner was told the numbers and may change them)
- Generation scores up to 5000 combinations per request: a user may have outfits made
  20 times a minute (`outfits.GeneratePerUser`); the next attempt is `RATE_LIMITED`
  with `Retry-After`. A request the gate refuses is not counted.
- A cell that is not in the cache makes the server ask a third party, whose free
  allowance is 10 000 questions a day: a user may cause 30 such questions an hour
  (`weather.AskPerUser`) and everyone together 300 (`weather.AskShared`). Past that the
  weather route answers `RATE_LIMITED` with `Retry-After`, and generation makes outfits
  without the weather. What the cache answers costs nothing. (First proposed as 60
  weather requests an hour; counting the questions to the provider bounds what matters
  and leaves the cache free.)
- The Next.js API has neither limit; until the cutover the contract lists a 429 for
  these two routes that only the Go server gives.
- Not limited in this stage, for the owner: how many outfits and how much feedback a
  user may store (the Next.js API has no limit either; a refusal would need a response
  the contract does not list for saving).

## Contract impact

Additive: `429 RATE_LIMITED` with `Retry-After` on `POST /outfits/generate` and
`GET /weather/current` (`apps/web/src/server/openapi/registry.ts`, the contract
regenerated). The generated Dart client did not change (it does not model error
responses; `generate_api.sh --check` passes); the mobile app already shows
`RATE_LIMITED` from any route as "too many attempts, try again later".

## Testing

Seam: the HTTP handlers over the real router, gate and PostgreSQL; the engine through
its one entry point; the weather client against a stand-in HTTP server.

- Engine: every golden case (seeded wardrobes of every size and mix, each occasion,
  weather band and edge, colour profiles, feedback, seeds, the candidate cap); the
  tables equal to the TypeScript ones; JavaScript-arithmetic helpers on their edge values.
- Request rules: golden vectors from the real schemas for the six requests.
- Weather: cache hit and miss, expiry, rounding of what leaves the server, the six-hour
  window, incomplete and failing answers (nothing cached), timeout.
- Generation: empty and one-sided wardrobes (each message), weather from the client,
  from the cache, from the service, and without; feedback shaping; another user's
  items never used; the answer equal to the Next.js one for the e2e wardrobe.
- Outfits: save (each refusal), list (all, saved), read, patch, delete, feedback (each
  kind, with the saved flag), ownership on every route.
- e2e: the whole browser suite in Go mode with these routes answered by Go.

## Out of scope

- AI reranking and explanations, the outfit-explanation quota, monitoring (B6).
- Paging of the outfit list; a weather error code of its own (contract changes).
- Hourly or daily forecasts.

## Security gate

Checklists of `lookly-security` for what the stage touches.

- **Quotas and abuse.** Expensive endpoints have per-user limits: generation and the
  questions to the weather service do now (Limits). Yes (tested). Open, for the owner:
  no bound on how many outfits and feedback rows a user stores.
- **Deny by default.** The eight new routes need a session and a current consent (the
  gate's default; tested on each), and every query names the owner: another user's
  outfit is `NOT_FOUND`, another user's item cannot be saved into an outfit
  (`FORBIDDEN`) and is not shown if a row links it. Yes (tested).
- **Untrusted input.** Bodies, the list's query, the coordinates and the path id are
  judged at the gate by golden-held rules (the bodies are fuzzed too); the weather service's answer is
  read with a size bound, strict types and ranges, with no redirect followed; stored
  JSON is decoded strictly. Yes (tested).
- **Outbound calls.** One fixed host; the place leaves the server rounded to about a
  kilometre and is in no log or error; no credentials are sent. Yes (tested).
- **Web cookies and CSRF.** The writes are behind the gate's cross-site guard. Yes
  (tested on each writing route).
- **Media.** Outfit answers carry signed links only, never storage keys. Yes (tested).
- **Fail closed.** `WEATHER_PROVIDER`: an unknown value stops the server; the mock is
  refused in production and staging. Yes (tested).
- **Secrets and CI.** gitleaks clean on the changed files; zizmor clean; no new module
  (`golang.org/x/sync` was in the module graph already). govulncheck: no
  vulnerabilities.
